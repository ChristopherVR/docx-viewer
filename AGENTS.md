# Working agreements

- One framework-neutral document model and one web-component editor. UI bindings are lifecycle/event adapters only.
- Published packages (like pptx-viewer): `docx-core` and one self-contained `docx-<framework>-viewer` per framework (react, vue, angular, svelte, solid, vanilla; vanilla also owns the plain `<docx-editor>` entry and `mountEditor`). `web-component` and `bindings` are `private: true` internal packages bundled into every framework package by `scripts/build-packages.mjs`; a published tarball may import only `docx-core`, `@christophervr/ooxml-core` (layout, document loading and the legacy `.doc` reader come from its `/docx/layout` and `/docx/load` entries, collaboration helpers from `/collab`), ProseMirror and its framework peers (`bun run check:published`, `bun run pack:smoke`). Never add `@christophervr/ole2` or an internal package to a manifest here: the core inlines the ole2 codecs. The browser `createCanvasMeasurer` stays in `packages/web-component/src/canvas-measurer.ts` and is injected into the core's layout engine.
- Keep source modules below 300 lines where practical. Add meaningful regression tests for parsing, preservation, editing and binding contracts.
- Unsupported document features must be reported honestly. Never silently claim Word layout parity or lossless export.
- Shared OLE and legacy Word implementations live in ../ole2 and reach this repository only through `@christophervr/ooxml-core/docx/load` (which inlines them); do not fork them or add an ole2 dependency here. Record extraction provenance.
- Use Bun, TypeScript strict mode, Vitest and browser contract tests. No commits or publishing unless requested.

- The DOCX model, parser, serializer and editing logic live in the `docx` area of the published `@christophervr/ooxml-core` package (`@christophervr/ooxml-core/docx`, source in the sibling `../ooxml-core` repository); `packages/core` (`docx-core`) is only a thin re-export of `/docx` and `/docx/embedded`. Its /embedded entry is ready for a future PowerPoint migration. Keep ole2 restricted to legacy compound-file codecs; never move modern OOXML handling into it.
- All Office logic is moving into the separate public repository `ChristopherVR/ooxml-core`, published to npm as the single package `@christophervr/ooxml-core` (areas are subpath imports such as `@christophervr/ooxml-core/xml`). This repository is meant to end up holding only the UI (web component, framework bindings, ribbon and dialog views, demos, browser tests); do not add new logic here that belongs in the core, and do not copy or fork what lives there. Today the units, XML, OPC and DOCX (model, parser, serializer, editing, ECMA-376 schema-validity tests) areas are consumed from it; the Word fixtures used by browser specs are copied into `tests/support`; `docs/ooxml-core-plan.md` has the plan. This repository depends on the published version (`^0.1.0`); to develop against local core changes, temporarily point `packages/core` at a sibling checkout with a `file:../../../ooxml-core` dependency (build it with `bun run build` first, then `bun install --force`) and restore the version range before committing.
